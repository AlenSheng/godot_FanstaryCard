# 临时放宽限流的真实对局压测

## 配置与恢复

用户授权临时放宽限制，结束后恢复。现有版本不支持关闭限流，因此采用允许的最高配置：HTTP窗口1秒，Auth/Admin/MarketRead/EconomyWrite各10000次/窗口，实时指令1000次/秒。不是完全禁用所有限制，协议尺寸、连接容量、业务校验和停止红线均未改动。

使用独立compose覆盖文件，不改原compose或镜像；服务器容器在设置和恢复时各重建一次。先部署服务端2小时兜底恢复任务，本机压测结束finally立即恢复并取消兜底任务。没有触发2小时兜底。

最终容器RequestLimits环境与原值一致（比较时仅顺序不同）：Auth=10，MarketRead=120，EconomyWrite=30；临时Window/Admin/Realtime覆盖已移除，回归原配置默认值。恢复后健康HTTP200，1.040秒。临时密钥副本和SSH隧道已清理，原始gpt.pem保留。

## 其他缺陷及优化空间

52个客户端报告 Expedition did not reach acknowledged settlement；失败检查集中于room_started（77次失败检查包括停止期间未进房检查，不能等同77个独立失败账号）。其中有首局结算后第二次匹配已收到ready_required/ready_accepted但30秒内没有room.started的记录。

需要优先检查压测驱动的准备确认时机、二次匹配状态清理与进房等待时长，并结合服务端匹配日志。不能把所有进房失败直接归责服务端；不能声称已验证100人持续同时战斗。

HTTP延迟包含客户端新连接、公网链路、重试及处理耗时，当前未分解；客户端每次HTTPRequest新建连接的代码提示连接复用可能有优化空间，但需单独测量证明。当前CPU/队列数据不足以支持直接扩容。

下一步先修正进房/循环流程，补充HTTP分阶段时间及发压机资源指标，再重复相同50/120秒负载。不要用抬高性能红线掩盖HTTP延迟。

证据：report.json、samples.jsonl、各客户端遥测和日志。正式限流已恢复，当前没有本轮压测继续运行。
