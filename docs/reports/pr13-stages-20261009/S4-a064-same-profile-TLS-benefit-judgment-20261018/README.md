# A06.4 同接口TLS收益裁决与反例

本轮验证了“变快”不能盖过错误：故障控制把原应成功的慢请求变成快速404，成功请求P95从938.005降到296.417ms，但失败从4增到5，保守裁决为Failed，候选没有通过。这个故障由本地夹具明确注入，不称为SUT自然退化。字节变化与组合变化两个真实控制均为DiagnosticOnly，未写成因果收益。

正常比较使用当前同源代码的per-request／reusable开关，三个活跃独立pair各保留同一TLS fixture/listener，按off/on、on/off、off/on顺序串行。每臂同一20请求组合：18顺序＋2并发尾部，路径／输入与原始响应字节签名逐槽相同。每臂16成功、4计划失败（2个HTTP404、2个截断），截止时2个pending，全部排空后pending为0。失败和pending不从分母删除，成功P95单列；全局分位数从原始请求计算，不平均各轮P95。

真实连接数每轮20→6，服务端观测复用率0→70%。全部终态平均时延是测前主指标，candidate−baseline三轮分别−9.8396、−9.83485、−10.85815ms，平均−10.17753ms。27个精确轮次cluster重采样的描述性区间约[−10.85815,−9.83485]ms，但只有3个独立轮次，8状态两侧sign-flip p=0.25，**收益仍Inconclusive，不把该描述区间当成95%生产收益或等效证明，不因样本不足写NoChange**。默认设置未改变，无运行时激活。

执行API是当前Gateway._request_http_transport及成功body的真实HTTP Protobuf codec，deadline3秒、headless进程帧上限240；不是完整REST重试／解码工作量或渲染TTI。本轮开头18项夹具／策略控制通过，当前66个TLS／close／chunked／压缩上限边界通过精确组件与函数身份复用，没有重跑。当前一次一连接路径是正常对照，不使用已知不安全的历史HTTPRequest参考。

首个校准臂20请求已全部终结，但探针用了实时schema而非HTTP schema，16个200因此语义校验误失败，原Native退出0／记录完整与旧控制器失败均保留，不改写为合格基线。修正探针为Proto.new(true)后启用新三pair批次，不把已关闭的旧服务端与新臂拼成同源。三个反例复用新首轮原基线，没有再跑基线。该观察器修正不改SUT／策略／固定组合／延迟，测前策略SHA仍与正式模块新增函数一致。

新批次180份应用层HTTP帧及180份原生body逐文件SHA核验；含原校准20和Python控制8，共208HTTP≤300，Native10≤12。所有Native有终态、TLS服务／线程／socket关闭；预算、正确性与95%标准均未放宽。正式分析模块只追加保守传输裁决，原游戏／容量函数保留，8项正式契约测试通过，实际数据用仓库函数重算与冻结策略逐字段一致。原始帧／body、所有失败和仅本地夹具源码留G盘，Git仅含正式分析代码／测试与精简报告。
