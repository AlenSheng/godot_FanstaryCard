# LOAD-06.1 三个LIVE案例通过，保留两轮未通过控制

R3使用当前未改的7项Gateway/协议源文件，原生Godot通过本地声明故障代理访问真实www.relicbound.cn。8个后端HTTP响应均为实际200，原始私有响应与令牌仅驻内存，公开文件仅状态、时序和哈希。TLS证书和域名校验始终开启，复用7次同一上游连接，系统信任库与云端配置未改。零游戏房间、零自然局、零源码上传。

T01的实际POST realtime/ticket丢弃前两个原始响应后，由Gateway进行两次重试，三个实际收包的写幂等键、trace键与请求体哈希完全一致，三个attempt和一个logical终态同ID。三个票据响应哈希各异；这里只证明客户端写键稳定，不宣称该票据端点只签发一次或证明资产幂等。T02延迟真实players/me响应，在请求未完成时切换声明的cycle/phase；完成后attempt与logical仍归旧cycle，而当前标签已更新。这不是两个物理游戏局，也不替代B01的真实房间上下文测试。T03实际10秒超时后重试成功，另一个原始200响应声明破坏为非法protobuf wire字节0f，准确保留decode_error attempt与error logical终态。

**R1默认Python证书链失败，没有完成任何后端HTTP请求；R2出现额外公网TLS/TCP超时和EOF，三个原生控制判定均Failed，原件未改成通过。** R3复用此前验证过的Windows任务专用有效信任链并保持严格验证；上游连接复用、补记每次代理收包、旧请求外部等待由18秒改为32.5秒（覆盖Gateway既有30秒logical上限）。这些仅为测试控制修正，客户端10秒attempt/30秒logical限制未改，没有放宽业务通过标准。R3三个控制才达到预登记的实际故障条件。

**旧PG覆盖纠正：原T01实际是GET players/me，2个attempt/1次重试，无写幂等键；不等于要求的两次重试且写键不变。** 原生行验证的stable断言确实通过，原结果保持Passed；撤销的是该行覆盖完整规范T01 POSTGRES的旧映射。本轮补三项LIVE后重新打开T01 POSTGRES，整项保持Partial。旧PG的T02/T03及单次GET重试事实不因此作废；复用层与per-request旧分支差别继续明确，不宣称当前全源等价。

本轮所有进程与代理已结束，无游戏/资产状态待清理。R1/R2/R3固定控制标签分别保留在不同目录，不据此宣称生产进程epoch唯一性。原生失败、范围限制与当前缺口均在case-review中可查。
